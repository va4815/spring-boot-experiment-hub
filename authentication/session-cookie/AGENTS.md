# Session + Cookie Authentication

## Purpose

This project implements **production-quality stateful authentication using Spring Security, server-side HTTP sessions, and session cookies**.

The project demonstrates the following authentication model:

```text id="6ozzlm"
Username + Password
        ↓
Spring Security Authentication
        ↓
user_account lookup
        ↓
Password verification
        ↓
Role resolution
        ↓
Authenticated SecurityContext
        ↓
HTTP Session
        ↓
JSESSIONID Cookie
        ↓
Subsequent authenticated requests
```

The implementation should follow production-level Java and Spring Boot engineering practices while preserving the defining characteristic of this experiment:

**authentication state is maintained server-side and referenced by a session cookie.**

# Database Model

The existing database schema is defined by `setup.sql`.

Treat the existing schema as the source of truth unless the task explicitly requires a schema change.

The authentication model contains two tables:

```text id="nwif3s"
role
├── id
├── code
└── name

user_account
├── id
├── username
├── password
└── role_id
      │
      └──────→ role.id
```

Relationship:

```text id="c60s2f"
role
  1
  │
  │
  N
user_account
```

A user account has exactly one role.

A role may be assigned to multiple user accounts.

Do not introduce many-to-many role mappings unless explicitly requested.

## `role` Table

The existing schema is:

```sql id="adot4x"
CREATE TABLE role
(
    id   INTEGER GENERATED BY DEFAULT AS IDENTITY,
    code VARCHAR(100) NOT NULL,
    name VARCHAR(100) NOT NULL,

    CONSTRAINT pk_role PRIMARY KEY (id),
    CONSTRAINT uk_role_code UNIQUE (code)
);
```

The role `code` is the stable value used for authorisation.

Existing roles are:

```text id="f2pum8"
SHOP_MANAGER
STAFF
```

Do not hard-code database role IDs because identity values are persistence details.

Resolve roles using their persisted relationship or stable role code as appropriate.

## `user_account` Table

The existing schema is:

```sql id="3krfpz"
CREATE TABLE user_account
(
    id       INTEGER GENERATED BY DEFAULT AS IDENTITY,
    username VARCHAR(255) NOT NULL,
    password VARCHAR(255) NOT NULL,
    role_id  INTEGER      NOT NULL,

    CONSTRAINT pk_user_account PRIMARY KEY (id),
    CONSTRAINT uk_user_account_username UNIQUE (username),
    CONSTRAINT fk_user_account_role
        FOREIGN KEY (role_id)
        REFERENCES role (id)
);
```

`user_account` is the source of truth for persisted authentication identities.

Do not rename or replace it with:

- `user`
- `users`
- `account`
- an in-memory user store

unless explicitly requested.

The `username` column uniquely identifies a user for authentication.

The `password` column contains a password hash, not a plaintext password.

The `role_id` column references the user's role.

Conceptually:


The user lookup should retrieve the information necessary for authentication and authorisation.

Handle unknown usernames using the appropriate Spring Security authentication semantics.

Do not expose persistence-specific failures to clients.

Conceptually:

```text id="t16dd1"

    ├── username
    ├── password
    └── Role
          │
```

Prefer a dedicated `UserDetails` representation or adapter rather than making the persistence entity depend directly on Spring Security interfaces merely for convenience.

# Password Handling

The existing seeded password uses BCrypt.

Use a Spring Security `PasswordEncoder` compatible with the stored BCrypt hash.

Password verification should conceptually be:

```text id="ybvs76"
submitted password
        │
        ▼
PasswordEncoder.matches(...)
        ▲
        │
BCrypt hash from user_account.password
```

Requirements:

- never store plaintext passwords
- never manually compare passwords
- never decrypt passwords
- never log passwords
- never log password hashes
- never return password hashes
- never include passwords in `toString()`
- never expose passwords through DTOs

If new users are introduced, encode passwords before persistence.

# Role-Based Authorisation

The user's authority originates from:

```text id="ml92kj"
user_account.role_id
        ↓
role.id
        ↓
role.code
```

Use `role.code` as the stable application-level authorisation value.

Existing role codes are:

```text id="7gzrgl"

STAFF
```

Do not use `role.name` for security decisions.

Do not trust role information supplied by clients.

Be deliberate about Spring Security's `ROLE_` convention.

If authorities are represented as:

```text id="v03dwq"

ROLE_STAFF
```

keep that mapping consistent throughout the project.

Do not mix:

```text id="j91qps"
SHOP_MANAGER
ROLE_SHOP_MANAGER
```

without understanding whether the API being used expects a role or a raw authority.

# Session Authentication

After successful credential authentication:

1. Spring Security creates an authenticated `Authentication`.
2. The `Authentication` is stored in the `SecurityContext`.
3. The security context is associated with the HTTP session.
4. The server sends the session identifier to the client.
5. The client sends the session cookie on subsequent requests.
6. Spring Security restores the security context from the session.
7. Protected endpoints use the restored authentication.

Conceptually:

```text id="hd7ag5"
Initial login

username/password
       ↓
Database authentication
       ↓
SecurityContext
       ↓
HTTP Session
       ↓
JSESSIONID


Subsequent request

JSESSIONID
       ↓
HTTP Session
       ↓
SecurityContext
       ↓
Authentication
       ↓
Controller / Service
```

Do not re-authenticate username/password on every request.

Do not query `user_account` on every request merely to prove that the user is authenticated when a valid authenticated session already provides that information.

A database lookup may still be appropriate when current mutable user information is required.

# Session Management

The application is intentionally stateful.

Do not configure:

```java id="aqkrrk"
SessionCreationPolicy.STATELESS
```

for the normal authentication flow.

Use Spring Security's established session-management capabilities.

Consider:

- session creation
- session fixation protection
- session timeout
- invalid sessions
- expired sessions
- logout invalidation
- concurrent sessions where required

Do not implement a custom session mechanism when Spring Security or the servlet container already provides the required behaviour.

# Session Fixation

Successful authentication must be protected against session fixation.

Use Spring Security's built-in session fixation protection unless there is a documented reason not to.

Do not preserve a client-controlled pre-authentication session identifier as the authenticated session without appropriate protection.

# Session Cookie

The session cookie is security-sensitive.

Production configuration should consider:

- `HttpOnly`
- `Secure`
- `SameSite`
- cookie path
- session lifetime

The cookie contains a session identifier.

It must not contain:

- username/password credentials
- password hashes
- complete user records
- role records

Production authentication cookies must be transmitted over HTTPS.

# CSRF

Cookie-based browser authentication requires deliberate CSRF protection.

Do not globally disable CSRF merely to simplify testing.

For authenticated state-changing requests, preserve Spring Security's CSRF protection unless another mitigation is explicitly designed and justified.

Remember:

```text id="ejt85v"
CORS ≠ CSRF protection
```

When modifying CSRF behaviour, consider:

- login
- logout
- POST/PUT/PATCH/DELETE requests
- browser clients
- frontend integration
- CSRF token retrieval and submission

Add tests for important CSRF behaviour.

# CORS

Configure CORS only when cross-origin browser access is required.

When credentials are permitted:

- explicitly configure trusted origins
- do not use unrestricted origins
- understand browser credential behaviour
- do not treat CORS as authentication or CSRF protection

Avoid permissive configuration simply to make development easier.

# Logout

Logout must invalidate the authenticated session.

Expected behaviour:

```text id="87eg35"
Authenticated session
        ↓
Logout
        ↓
Session invalidated
        ↓
SecurityContext removed
        ↓
Previous JSESSIONID
cannot authenticate requests
```

Prefer Spring Security's logout support.

Tests should verify that the previous session cannot access protected resources after logout.

# API Design

Controllers should remain focused on HTTP concerns.

Do not place:

- password verification
- repository authentication logic
- session persistence logic
- role lookup logic

directly in controllers.

Use appropriate DTOs for request and response contracts.

Never return `UserAccount` entities directly if doing so risks exposing persistence or credential fields.

# Error Handling

Handle security failures consistently.

Relevant scenarios include:

- unknown username
- incorrect password
- unauthenticated request
- invalid session
- expired session
- insufficient authority
- invalid CSRF token

Use appropriate HTTP semantics.

Generally distinguish:

```text id="3cl31v"
401 Unauthorized
    → authentication is missing or invalid

403 Forbidden
    → authenticated but not permitted
      or request rejected by security policy
```

Avoid exposing whether a username exists when doing so unnecessarily assists account enumeration.

Never expose stack traces, SQL errors, password hashes, or internal security details through API responses.

# Logging

Never log:

- plaintext passwords
- password hashes
- complete JSESSIONID values
- session cookies
- CSRF secrets/tokens

Security logging may include appropriate events such as:

- successful authentication
- failed authentication
- logout
- session expiration
- relevant authorisation failures

Logs should provide operational value without leaking credentials.

# Testing Requirements

Authentication and session behaviour should be covered by tests.

Where applicable, verify:

1. `admin` can authenticate with the correct password.
2. Incorrect passwords are rejected.
3. Unknown usernames are rejected.
4. Unauthenticated requests cannot access protected resources.
5. Successful login creates an authenticated session.
6. The returned session can authenticate subsequent requests.
7. The authenticated principal represents the correct `user_account`.
8. `SHOP_MANAGER` is mapped to the expected Spring Security authority.
9. Authorisation rules reject insufficient roles.
10. Logout invalidates the session.
11. The previous session cannot authenticate after logout.
12. Session fixation protection behaves correctly.
13. Invalid/expired sessions are rejected.
14. CSRF protection applies to relevant state-changing operations.
15. Missing/invalid CSRF tokens are rejected where required.

Use Spring Security's test support where appropriate.

Prefer behaviour-focused tests rather than tests tightly coupled to framework internals.
